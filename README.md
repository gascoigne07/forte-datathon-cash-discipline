# Контроль кассовой дисциплины по видеозаписи

Решение кейса ForteBank (Datathon 26). Сервис принимает видеозапись рабочего места кассира,
находит визуально наблюдаемые признаки возможных нарушений и показывает проверяющему
кадр-доказательство, таймкод, тип события и ссылку на норматив Республики Казахстан.

**Всё работает локально.** Облачные AI-сервисы и API не используются ни на одном этапе
обработки (раздел 7 ТЗ, п.21 и п.35 FAQ). После загрузки весов интернет не нужен —
проверяется запуском с `HF_HUB_OFFLINE=1`.

---

## 1. Запуск

```bash
# 1. окружение (один раз)
uv venv --python 3.12 .venv
VIRTUAL_ENV=.venv uv pip install torch torchvision transformers timm pillow numpy scipy \
    scikit-learn opencv-python-headless fastapi "uvicorn[standard]" python-multipart einops

# 2. веса моделей (один раз, нужен интернет)
.venv/bin/python -c "from huggingface_hub import snapshot_download as d; \
    d('florence-community/Florence-2-large'); d('PekingU/rtdetr_v2_r50vd')"

# 3. сервис
./run.sh              # http://127.0.0.1:8000
./run.sh --tunnel     # то же + публичный URL через Cloudflare Tunnel
```

API-ключ печатается при старте и сохраняется в `.api_key`. Задать свой: `API_KEY=... ./run.sh`.
Полный офлайн: `HF_HUB_OFFLINE=1 ./run.sh`.

### Переменные окружения

Поведение настраивается без правки кода — это нужно, если решение переносится на
машину с GPU (там Florence-2 стоит ~0.2 с/кадр вместо 2.7, и бюджет кадров можно
поднять в разы).

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `API_KEY` | генерируется в `.api_key` | ключ для заголовка `X-API-Key` |
| `PORT` | `8000` | порт HTTP |
| `HF_HUB_OFFLINE` | `0` | `1` — полный офлайн, веса только из локального кэша |
| `KF_CAP` | `45` | максимум кадров, уходящих в модель описания, на одно видео |
| `KF_STEP_SEC` | `1.5` | минимальный шаг между ключевыми кадрами |
| `WORKERS` | `1` | параллельных анализов. На Apple M4 оставить 1: обе модели на одном MPS-устройстве, два анализа втрое замедляют друг друга и приводят к убийству процесса по памяти |
| `CAPTION_MODEL` | `microsoft/Florence-2-large` | модель описания кадра |
| `ANALYZE_BUDGET_SEC` | `260` | бюджет одного анализа, если дедлайн не задан |
| `JOB_DEADLINE_SEC` | `285` | абсолютный дедлайн от постановки в очередь |
| `MAX_UPLOAD_MB` | `200` | предел размера загружаемого файла |
| `NOVELTY` | `0` | `1` включает канал новизны (измерен, не разделяет классы — см. раздел 7) |

## 2. API для жюри (раздел 10 ТЗ)

```bash
curl -X POST https://<адрес>/api/v1/analyze \
     -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
# -> {"job_id":"3f2a9c1e","status":"processing"}

curl https://<адрес>/api/v1/jobs/3f2a9c1e -H "X-API-Key: <ключ>"
```

При `status: done` возвращается схема из ТЗ: `verdict` (`violation` / `no_violation`),
`violations[]` с полями `type`, `timecode_sec`, `description`, `evidence_frames[].image_base64`.
Интерактивная документация: `/api/docs`.

Сверх схемы ТЗ — необязательные поля, которые жюри может игнорировать. Они добавлены
не для красоты: каждое отвечает на вопрос «на чём основан вывод и можно ли ему верить».

| Поле | Зачем |
|---|---|
| `violations[].confidence` | уверенность правила, растёт с числом подтвердивших кадров |
| `violations[].window_sec` | интервал, на котором признак наблюдается, а не одна секунда |
| `violations[].rule` | норматив: реквизиты акта, пункт, **редакция пункта**, дословная цитата, ссылка на adilet, флаг `verified` (`false` = это трактовка нормы, а не дословный запрет) |
| `low_coverage` | `true` — сервис успел посмотреть слишком мало кадров, вердикту доверять нельзя |
| `frames_analyzed` / `frames_total_sampled` | сколько кадров разобрано из сетки 2 fps |
| `zone_source` | как выведена зона столешницы: `wood` (тон дерева) / `anchors` (статичная техника) / `roi` (объединение детекций) / `fallback` (константа). На незнакомом ракурсе видно, выведена зона из сцены или сервис скатился в константу |

Коды ошибок: без верного `X-API-Key` — **401**, не видеофайл — **400**, файл больше
200 МБ — **413**, неизвестный `job_id` — **404**. Все проверены живым прогоном.

## 3. Архитектура

Каскад «дешёвое → дорогое»: уложиться в 5 минут на видео можно, только если тяжёлая
модель запускается по десяткам кадров, а не по всем четырём тысячам.

| Этап | Чем | Стоимость |
|---|---|---|
| 1. Декодирование, выборка 2 к/с | OpenCV | 145-секундное видео → ~290 кадров вместо 4350 |
| 2. Детекция людей и предметов | **RT-DETR v2** (Apache-2.0) | ~40 мс/кадр |
| 3. Геометрия сцены: медианный фон, зона столешницы, счётная машина | классический CV | ~1 с на видео |
| 4. Треки новых предметов на столешнице | вычитание фона + трекинг блобов | ~1 с на видео |
| 5. Описание ключевых кадров | **Florence-2-large** (MIT) | 2.7 с/кадр |
| 6. Разбор описаний в факты | детерминированный код | мгновенно |
| 7. Правила над фактами → события | `service/app/rules.py` | мгновенно |
| 8. Кадры-доказательства и обоснование | OpenCV | ~1 с |

Ключевые кадры выбираются не равномерной сеткой, а по смене числа людей, пикам движения
и моментам появления предметов на столе — туда, где что-то меняется.

### Почему так, а не иначе

- **Почему Florence-2, а не Qwen2.5-VL-7B.** Замеряли обе: Qwen на Apple M4 даёт ~4 токена/с,
  это 13 с на кадр и 12–18 кадров на видео в лимит. Florence-2-large — 2.7 с/кадр при лучшем
  качестве на нужных нам объектах (стакан, сумки). Лицензия MIT чище Apache-2.0 для передачи
  прав заказчику (п.34 ТЗ).
- **Почему зона столешницы ищется по тону дерева на медианном фоне, а не по координатам.**
  Камера в обучающем датасете переставлялась между записями, финальное видео жюри снято
  под другим углом (п.4 FAQ). Пиксельные константы это ломает, а относительная геометрия — нет.
- **Почему факты извлекаются из текстового описания, а не из булевых ответов модели.**
  При запросе JSON с девятью флагами модель схлопывалась в «всё false», хотя в свободном
  тексте писала «клиент держит банкноты». Описание + разбор ключевых слов в коде устойчивее.
- **Почему каждый предметный признак требует подтверждения на двух кадрах.** Модель ошибается
  на отдельных кадрах в обе стороны; голосование по соседним кадрам гасит одиночные ошибки
  (приём из AnomalyRuler, ECCV'24).
- **Почему важен предлог в описании.** На чистом ролике `Х-16` модель пишет «a man holding a
  green bag» — сумку несут; на нарушении `Х-15` — «a green office bag on the desk» — сумка
  брошена на столешнице. Без разбора контекста это был бы один и тот же факт и ложное срабатывание.

### О выборе рабочей точки

ТЗ прямо ставит пропуск выше ложного срабатывания: «ложных срабатываний должно быть
как можно меньше, пропуск нарушения недопустим» (п.16 FAQ). Поэтому рабочая точка
выбрана как **максимум полноты при ложных ≤ 2 из 19 чистых роликов**. Перебор
вариантов правил — `tools/sweep_rules.py`, итог переизмерен через `tools/eval_caps.py`.

| Вариант правил | Найдено | Ложных | Вердикт | Δt медиана |
|---|---|---|---|---|
| только предметные правила (напиток, сумки) | 4 | 0 | 62 % | 2.0 с |
| + рабочее место без работника, трек ≥ 60 | 9 | 1 | 68 % | 2.1 с |
| + рабочее место без работника, трек ≥ 45 | 9 | 2 | 65 % | 3.0 с |
| + посторонние 3+ и предмет, серия 2 кадра | 12 | 4 | 68 % | 3.0 с |
| **+ посторонние 3+ и предмет, серия 3 кадра** | **11** | **1** | **72 %** | 3.0 с |
| + посторонние 3+ и предмет, серия 4 кадра | 10 | 1 | 70 % | 3.0 с |

Выбрана выделенная строка: полнота выросла с 43 % до 52 % без новых ложных
срабатываний, платой стала точность таймкода (медиана 2.1 → 3.0 с). Критерий 1
весит 25 баллов против 15 у критерия 2, поэтому обмен оправдан.

Единственное ложное срабатывание (`Х-12`) разобрано: описание кадра перечисляет только
технику, человек не упомянут, и на столешнице зафиксировано изменение. Наблюдаемая
картина совпадает с нарушением — различить их по видео нельзя.


## 5. Устойчивость (критерий 5)

Финальное видео жюри снято под другим углом (п.4 FAQ), поэтому устойчивость
проверена измерением. Набор искажений собран по таксономии бенчмарка устойчивости
пространственно-временных моделей (NeurIPS 2021 Datasets & Benchmarks): движение
камеры, освещение, размытие, шум, цифровые артефакты, временные. Каждый вариант
прогнан через боевой пайплайн целиком (`tools/augment.py` + `tools/run_pipeline.py`).

`tools/smoke_new_angle.py` на всех 32 вариантах: зона столешницы ни в одном случае не
скатилась в константу «нижние две трети» (31 вариант по тону дерева, ч/б — по статичной
технике, и на нём нарушение всё равно найдено).

### Где именно проходит граница

Вместо бинарного «ломается / не ломается» прогнана развёртка по силе искажения:

- **Сжатие.** Исходный ролик — 1627 кбит/с. Распознавание держится при CRF 28, то есть
  на **82 кбит/с — двадцатикратном сжатии**, и ломается при CRF 34 (37 кбит/с, сорокачетырёхкратное).
  Ролики жюри примерно того же битрейта, что обучающие, то есть запас по сжатию — порядок величины.
- **Размытие.** Держится до σ=1.2 включительно, ломается на размытии движения
  (усреднение соседних кадров плюс боксовый фильтр).
- **Поворот.** Держится и на +7°, и на +15°, и в составном варианте «зеркало плюс поворот».
- **Цвет.** Перевод в чёрно-белое не ломает: признак не завязан на цвет предмета.

### Ложных срабатываний искажения не добавляют

Чистые ролики прогнаны через 10 вариантов искажений — **во всех 10 случаях
«нарушение не обнаружено»**. Устойчивость достигнута не ценой роста ложных срабатываний.

Числа в таблицах считаны скриптом из файлов прогонов `data/runs/`, а не выписаны вручную.

### Чувствительность на незнакомом фоне: вклеенные предметы

Отдельная проверка (`tools/plant_object.py`): в чистые ролики, где правила заведомо
ничего не находят, вклеены реальные вырезки предметов из датасета начиная с известной
секунды — эллиптическая маска с растушёвкой, яркость подогнана под локальный фон.
Это измеряет **чувствительность** на фоне, под который ничего не настраивалось.

| Ролик | Предмет | Размер в кадре | Результат |
|---|---|---|---|
| `Х-21` | банка | 12×22 px | ✅ найдено на 5.0 с |
| `Х-29` | сумка | 52×36 px | ❌ |
| `Х-3` | стакан | 18×24 px | ❌ |
| `Х-43` | стакан | 18×24 px | ❌ |
| `Х-43` | стакан ×1.5 | 27×36 px | ✅ на 17.0 с |
| `Х-43` | стакан ×2.0 | 36×48 px | ✅ на 18.0 с |
| `Х-43` | банка ×1.5 | 18×33 px | ✅ на 14.0 с |
| `Х-3` | банка ×1.5 | 18×33 px | ✅ на 15.0 с |
| `Х-43` | сумка ×1.5 | 78×54 px | ✅ на 18.0 с |
| `Х-3` | сумка ×1.5 | 78×54 px | ❌ |

**6 вклеек из 10. В исходном размере — 1 из 4, при увеличении от 1.5× — 5 из 6.**

Вывод точнее, чем «дело в размере». Размер решает в основном: тот же стакан в том же
месте того же ролика не находится при 18×24 пикселях и находится при 27×36. Но не
только: сумка 78×54 — самый крупный вклеенный предмет — найдена на `Х-43` и не найдена
на `Х-3`, потому что бежевая сумка на светлой столешнице почти не контрастирует с фоном,
а бирюзовая банка 18×33 различается уверенно на обоих фонах.

**Предел решения — различимость предмета на столешнице: сочетание размера и контраста,
а не один размер.** Это согласуется с главным ограничением из раздела 7: банкноты не
распознаются именно потому, что они мелкие И по тону близки к дереву стола.

Таймкод у вклеенных предметов хуже (17–18 с против вклейки с 8.2 с): предмет
появляется без участия человека, и момент появления правило привязывает к первому
кадру, где описание перестаёт упоминать людей.

Опорная геометрия — зона столешницы — определяется на искажённых копиях с отклонением
не более 19 % по ширине и 9 % по центру (12 вариантов из 12 в допуске). Изначально
затемнение сбивало зону на 39 %: порог яркости был фиксированным. После перехода на
относительный порог от медианы кадра расхождение ушло.

## 5a. Поведение под нагрузкой жюри (5+ видео)

Жюри прогоняет 5 и более тестовых видео (п.12 FAQ), а лимит 5 минут считается
для каждого видео. Если обрабатывать каждое по максимуму, последнее в очереди
израсходует свой лимит, ещё не начав обрабатываться. Проверено измерением.

**Прогон 5 видео, отправленных подряд:** все 5 вердиктов верные (3 нарушения,
2 чистых), обработка 39–69 с на ролик, последний финишировал на 285-й секунде
от отправки — впритык к лимиту.

Отсюда два механизма:
- число разбираемых кадров уменьшается, когда очередь не пуста (`jobs.pending()`);
- дедлайн **абсолютный**, от момента постановки в очередь, а не от старта обработки:
  время ожидания вычитается из бюджета этого видео.

Нижняя граница урезания — **18 кадров**, и это замер, а не оценка. Прогон правил по
прореженному корпусу:

| Кадров на ролик | Найдено | Ложных | Вердикт | Что теряется |
|---|---|---|---|---|
| 45 / 25 / 18 | 11 | 1 | **72 %** | — |
| 15 | 11 | 2 | 70 % | добавляется ложное срабатывание |
| 13 | 9 | 2 | 65 % | `Х-4`, `Х-26` |
| 12 | 9 | 1 | 68 % | `Х-26`, `Х-40` |

До 18 кадров метрика полная, ниже — осыпается. Граница безопасна, потому что реальным
ограничителем остаётся абсолютный дедлайн: не хватит времени — цикл оборвётся сам и
выставит `low_coverage`. В первой версии граница была 12, и на приёмочном прогоне
`Х-40` получил 13 кадров и вернул `no_violation` — дефект найден только живым прогоном,
офлайн-замер его не видел.

**Прогон 5 видео после подъёма границы до 18 кадров** (лимит считается от отправки
каждого, как у жюри): `Х-46` 58 с, `Х-40` 110 с, `Х-15` 161 с, `Х-10` 210 с,
`Х-4` 271 с — **5 из 5 в лимите, 5 из 5 вердиктов верных**. Контракт раздела 10
проверен на всех пяти ответах (`tools/validate_response.py`): по три кадра-
доказательства, норматив с дословной цитатой и указанием редакции пункта.

**Прогон 7 видео подряд:** все 7 вердиктов верные, шесть разобраны
нормально (12–22 кадра, 36–65 с), седьмой упёрся в дедлайн и вернулся с флагом
`low_coverage: true` — сервис честно сообщает, что успел посмотреть один кадр
и вердикту доверять нельзя, вместо того чтобы молча выдать результат.

Интерфейс в этом случае показывает предупреждение «Неполный анализ».

## 6. Типы нарушений, которые распознаёт решение

| Тип | Наблюдаемый признак | Норматив |
|---|---|---|
| Напитки или еда на рабочем месте кассира | стакан, кружка, банка, бутылка на столе — на ≥2 кадрах | Правила № 231, п. 12 (трактовка, см. оговорку) |
| Личные вещи (сумка) на рабочем месте | сумка/рюкзак/пакет **лежит** на столе (не в руках) | Правила № 231, п. 12 |
| Инкассаторская сумка вне сейфа | сумка-мешок лежит на столешнице | Правила № 231, п. 24, 92, 106 |
| Рабочее место оставлено без работника, на столешнице предметы | описание кадра не упоминает ни одного человека, при этом перечисляет предметы на столе | Правила № 231, п. 20 |
| Наличные оставлены без контроля кассира | банкноты на столе, работника рядом нет | Правила № 231, п. 20 |
| Кассир покинул рабочее место, не убрав ценности | работника нет, при этом в ролике фигурируют ценности | Правила № 231, п. 22, 80 |
| Посторонний в кассовом помещении при операции с наличными | трое и более человек одновременно с наличными | Правила № 14, п. 16 |

Последние три типа реализованы и работают, но на обучающей выборке не сработали ни разу:
локальные модели на этом разрешении не отличают банкноты от бумаги (см. раздел 7).

Нормативная база с дословными цитатами: [`kb/NORMATIVE.md`](kb/NORMATIVE.md),
машинный вид — [`kb/rules.json`](kb/rules.json). **13 из 14 пунктов подтверждены дословно**
по полному тексту актов (проверено построчным сличением). Один пункт — про еду и напитки —
честно помечен `verified: false`: прямого запрета в актах нет, есть закрытый перечень
разрешённого к вносу в кассовый узел. Интерфейс показывает такую ссылку с пометкой
«трактовка, а не дословный запрет».

## 7. Ограничения и известные случаи ошибок

Раздел обязателен по п.8 ТЗ. Все утверждения ниже — результаты замеров, а не предположения;
подробности и числа в [`01-FINDINGS.md`](01-FINDINGS.md).

1. **Главное ограничение: банкноты не распознаются.** Пачка купюр на кадре 464×848 занимает
   ~25×15 пикселей. Проверены OWLv2, Florence-2 (base и large), Qwen2.5-VL (3B и 7B) —
   на тесном кропе настоящие купюры описываются как «business card» и «packet of chips»,
   а на чистом ролике без денег модель выдаёт «holding a small amount of money».
   Сигнал не просто слабый, а инвертированный, поэтому денежный канал в правилах
   реализован, но на практике не срабатывает.
2. **Полнота 52 %, ложное срабатывание 1 из 19.** Сервис находит предметные нарушения
   (напиток, сумки, оставленное без работника рабочее место) и пропускает поведенческие —
   как именно кассир обращается с наличностью. Ложное срабатывание (`Х-12`)
   возникает там, где работник на время выходит из кадра, а на столешнице фиксируется
   изменение: наблюдаемая картина совпадает с нарушением, различить их по видео нельзя.
   Роль проверяющего сервис не заменяет.
3. **Грубые признаки сцены сигнала не несут.** Измерено на 8 признаках (число людей,
   отсутствие кассира, энергия движения, новые предметы): AUC 0.33–0.59 при 0.5 = монетка.
   В чистых роликах кассир тоже встаёт и выходит (`Х-29`, `Х-31`), посторонние тоже заходят
   в кабину (`Х-35`, `Х-37`), предметы тоже лежат на столе (`Х-10`, `Х-14`, `Х-43`).
   Поэтому «кассир отошёл» сам по себе нарушением не считается.
4. **Обучение на датасете бесперспективно.** Эмбеддинги SigLIP + логистическая регрессия,
   протокол leave-one-out: точность 48 % при 50 % у монетки. 21 положительный пример —
   слишком мало для тонкого действия.
5. **Нарушения «по бездействию»** (кассир не выполнил обязательное действие) распознаются
   только там, где бездействие видно как отсутствие действия в кадре.
6. **Вывод не делается там, где нужны невидимые данные** — корректность проводки, сверка
   остатка (прямой запрет раздела 7 ТЗ). Все формулировки описаний это соблюдают.
7. **Звук не анализируется** (п.28), **лица не распознаются** (п.29) — используется только
   детекция людей как объектов, без идентификации.
8. **Один воркер:** видео обрабатываются по очереди, параллельный прогон двух роликов
   на 16 ГБ привёл бы к свопу и срыву лимита.
9. **Таймкод для предметов, присутствующих с первого кадра** указывается по первому
   наблюдению, а не по моменту, когда предмет стал нарушением (пример: `Х-24`, Δt = 8 с).
