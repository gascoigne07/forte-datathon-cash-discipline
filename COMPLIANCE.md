Сверка решения с техническим заданием, по пунктам
==================================================

Проверено построчно по документу `Кейс_ForteBank.docx` (ТЗ + FAQ). Для каждого требования
указано, где именно оно выполнено в коде. Таблица служит и чеклистом перед сдачей, и ответом
на вопрос жюри «а это вы предусмотрели?».

## Раздел 4. Обязательный пользовательский сценарий

| Требование ТЗ | Где реализовано | Статус |
|---|---|---|
| Пользователь открывает веб-интерфейс и загружает видеофайл | `service/static/index.html`, drag&drop + выбор файла | ✅ |
| Сервис запускает анализ и отображает статус обработки | `app.js` опрашивает `GET /api/v1/jobs/{id}` раз в 2 с, рисует прогресс-бар, стадию и прошедшее время | ✅ |
| Показывает один из двух результатов, **дословно** «Нарушение не обнаружено» / «Обнаружены признаки возможных нарушений» | `app.js:494` и `app.js:506` — формулировки совпадают с ТЗ буква в букву | ✅ |
| Для каждого нарушения (их может быть несколько) указывает тип, таймкод и описание | `pipeline.analyze` → `violations[]`, до 4 событий на ролик | ✅ |
| Показывает один или несколько кадров-доказательств из соответствующего фрагмента | `pipeline._evidence` — до 3 кадров: до события, на событии, после | ✅ |
| Кратко описывает, **что именно видно** на видео **и почему это может указывать на нарушение** | `pipeline._PHRASES` — две части на каждый тип; вторая связывает наблюдаемое с требованием норматива | ✅ |
| Указывает правило и нормативный источник: название документа, пункт/раздел | `rules.rule_ref` → блок «Норматив» в карточке: название, реквизиты, пункт, дословная цитата, ссылка | ✅ |
| Доступен через API, по нему жюри проверяет решения | `service/app/main.py`, раздел 10 ниже | ✅ |

## Раздел 5. Обязательные требования к результату

| Требование | Как выполнено | Статус |
|---|---|---|
| Работающий сервис: фронтенд и серверная часть, без ручного запуска кода | FastAPI + статический интерфейс, `./run.sh` | ✅ |
| Обнаружение визуально наблюдаемых действий | каскад RT-DETR → геометрия сцены → Florence-2 → правила | ✅ |
| Вердикт — один из двух результатов | `verdict`: `violation` / `no_violation`, третьего значения нет | ✅ |
| Таймкод для каждого события | `timecode_sec` у каждого элемента `violations[]` | ✅ |
| Кадр-доказательство, позволяющий человеку проверить вывод | на кадре вшит таймкод и обведена зона признака, кадр события выделен ярче (`perception.annotate`) | ✅ |
| Обоснование без неподтверждённых предположений | текст собирается детерминированно из фактов; вольный пересказ модели в вывод не попадает | ✅ |

## Раздел 7. Ограничения и допущения

| Ограничение | Как соблюдено | Статус |
|---|---|---|
| Анализ только по видео и открытым источникам | других источников нет | ✅ |
| Не утверждать нарушение там, где нужны невидимые данные (проводка, сверка) | ни одна формулировка не ссылается на учётные данные; вывод помечен как подсказка | ✅ |
| Результат — подсказка для человека, не заключение | фраза «окончательную оценку даёт проверяющий» в каждом описании | ✅ |
| Локальность: никаких облачных AI-сервисов, включая передачу кадров и их описаний | модели локальные (Florence-2, RT-DETR); проверяется запуском с `HF_HUB_OFFLINE=1`; наружу уходит только HTTP-вход туннеля | ✅ |
| Переносимость: после загрузки весов интернет не нужен | `Dockerfile` c весами внутри образа, `HF_HUB_OFFLINE=1` в окружении | ✅ |

## Раздел 10 и FAQ. API и регламент проверки

| Требование | Как выполнено | Статус |
|---|---|---|
| `POST /api/v1/analyze`, поле `file`, формат `.mov` → `job_id` | `main.analyze` | ✅ |
| `GET /api/v1/jobs/{job_id}` → `processing` / `done` / `failed` + результат | `main.job_status` | ✅ |
| Доступ по ключу в заголовке `X-API-Key`, запросы без ключа отклоняются | `main.require_key`, 401; сравнение через `secrets.compare_digest` | ✅ |
| Схема ответа: `verdict`, `violations[].type/timecode_sec/description/evidence_frames[].timestamp_sec/image_base64` | `schemas.py` — имена полей сверены с ТЗ побуквенно | ✅ |
| 1–3 кадра-доказательства, JPEG в base64 | ровно до 3 | ✅ |
| Лимит 5 минут на видео | бюджет 260 с + жёсткий стоп по остатку времени; при малом покрытии выставляется `low_coverage` | ✅ |
| Жюри прогоняет 5+ тестовых видео | очередь заданий; при непустой очереди число разбираемых кадров уменьшается, чтобы последнее видео не дождалось своего лимита в очереди (`jobs.pending` → `analyze(queued=...)`) | ✅ |
| Формат `.mov`, размер около 29 МБ (п.25) | принимается `.mov` и ещё четыре формата, лимит 200 МБ | ✅ |
| Публичный URL обязателен (п.23) | Cloudflare Tunnel, `./run.sh --tunnel` | ✅ |
| Язык интерфейса на выбор команды (п.26) | русский | ✅ |
| Авторизация, история, экспорт, пакетная загрузка не нужны (п.27) | не делали; выгрузка JSON добавлена как удобство | ✅ |
| Звук не использовать (п.28) | аудиодорожка не читается | ✅ |
| Лица не распознавать (п.29) | только детекция людей как объектов, без идентификации | ✅ |
| Оценка автоматическая, результат в JSON по единой схеме (п.18) | схема фиксирована в `schemas.py`, есть `/api/docs` | ✅ |
| Вердикта «Недостаточно данных» нет, злоупотребление им штрафуется (п.15) | такого значения в схеме нет | ✅ |
| Open source с коммерческой лицензией (п.24), права у банка (п.34) | Florence-2 — MIT, RT-DETR — Apache-2.0; Ultralytics YOLO (AGPL) намеренно исключён | ✅ |
| Дисквалификация за облачные решения по API (п.35) | сетевых вызовов при обработке нет | ✅ |

## Что сознательно НЕ сделано

| Что | Почему |
|---|---|
| Дообучение детектора на датасете | замерено: на 21 положительном примере обучение не даёт сигнала (leave-one-out 48 % при 50 % у монетки), см. `01-FINDINGS.md` |
| Повышение полноты за счёт ложных срабатываний | каждое срабатывание сопровождается ссылкой на пункт норматива; срабатывание «на всякий случай» обесценивает ссылку. Выбрана точка «максимум полноты при нуле ложных на 20 чистых роликах» |
| Вердикт «недостаточно данных» | не предусмотрен ТЗ и штрафуется (п.15) |
| Пакетная загрузка и история проверок | прямо названы необязательными (п.27) |
